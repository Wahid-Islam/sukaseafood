# SukaSeafood Price Forecasting — Backend Handoff & Operations Guide

## 1. Purpose

This document is the handoff guide for the SukaSeafood seafood price forecasting pipeline.

The forecasting system takes official, manually downloaded PriceCatcher CSV data, processes the data for the supported Selangor seafood items, selects a forecasting method per fish, produces four-week forecasts, adds a validated directional outlook where evidence is strong enough, and prepares database/API-ready staging outputs.

The production architecture is:

```text
Official PriceCatcher CSV
        |
        v
Raw data / mapping
        |
        v
R preprocessing + cleaning
        |
        v
Daily + weekly price series
        |
        v
Per-fish model evaluation
        |
        v
Forecast eligibility
        |
        v
Four-week production forecast
        |
        v
Directional outlook validation
        |
        v
Integrated production forecast
        |
        v
Database staging
        |
        v
SukaSeafood backend / database
        |
        v
API
        |
        v
SukaSeafood frontend
```

### Core architectural rule

**R is the forecasting engine. The backend/database is the persistence and delivery layer. The frontend does not run the R forecasting models.**

The backend should consume the production/staging outputs and expose them through the SukaSeafood API.

# 2. Important project rules

## 2.1 No scraping

**Scraping is not permitted in this project.**

PriceCatcher data is obtained through the official downloadable dataset and manually placed into the project's raw-data directory.

The refresh process must remain:

```text
Official PriceCatcher download
        ->
Place CSV in data/raw/
        ->
Run R refresh pipeline
        ->
Generate forecast outputs
        ->
Load into database
```

Do not replace this with website scraping, browser automation, reverse-engineered endpoints, or unofficial scraping methods.

The refresh manifest/logs explicitly record:

```text
scraping_used = FALSE
```

---

## 2.2 Canonical fish names must be preserved

`canonical_name` is the application's stable human-readable identity for the forecasting pipeline.

Do not create a second set of fish names in the backend.

The canonical names currently used are:

2. Bawal Putih
3. Cencaru
4. Demuduk / Cupak / Cermin
5. Ikan Gelama


# 5. PriceCatcher input process

The PriceCatcher dataset is updated daily.

The project does not scrape PriceCatcher.

When a new official dataset is downloaded:

1. Place the CSV in the appropriate `data/raw/YYYY/` directory.
2. Keep the official source file unchanged.
3. Do not overwrite historical source files unless deliberately maintaining an immutable source archive.
4. Run the refresh pipeline.
5. Inspect the refresh log and validation outputs.
6. Load the generated staging data into the backend/database.

The current historical raw-data layout contains monthly PriceCatcher files such as:

```text
data/raw/2025/pricecatcher_2025-01.csv
...
data/raw/2025/pricecatcher_2025-12.csv

data/raw/2026/pricecatcher_2026-01.csv
...
data/raw/2026/pricecatcher_2026-08.csv
```

The pipeline currently uses the accumulated raw data to build the historical price series.

# 6. Production pipeline execution order

## Preferred approach

Run:

```text
R:34_daily_forecast_refresh.R
```

This is intended to orchestrate the production refresh.

Conceptually, it runs the stages in this order:

```text

4. Build dense-fish ETS backtests

7. Build final forecast eligibility
8. Generate four-week production forecasts
9. Validate directional strategies
10. Integrate forecast + direction
11. Create database staging outputs
12. Validate final production outputs
```

# 7. What each production stage does

## Stage A — Multi-fish price series

Script:

```text
R:23 multi_fish_price_series.R
```

Purpose:

- Establish the multi-fish universe from the mapping.
- Connect PriceCatcher item data to canonical fish names.
- Focus the series on Selangor.
- Prepare the data used by later modelling stages.

---

## Stage 27 — Conservative cleaning

Script:

```text
R:27_multi_fish_cleaning.R
```

Purpose:

- Construct daily fish price summaries.
- Detect statistical extremes.
- Apply conservative high-confidence cleaning.
- Preserve high-support extremes instead of blindly removing every statistical outlier.
- Produce cleaned daily and weekly price series.

Important output files include:

```text
data/processed/multi_fish_selangor_daily_clean.csv
data/processed/multi_fish_selangor_weekly_clean.csv
outputs/multi_fish_outlier_summary.csv
outputs/multi_fish_high_confidence_removals.csv
outputs/multi_fish_high_support_extremes.csv
```

The cleaning approach deliberately avoids aggressive deletion.

For the August 2026 refresh, the reported retention was approximately:

- 99%+ of observations retained for each fish.
- Only high-confidence anomalies were removed.
- High-support extremes were retained and flagged.

---

## Stage 28 — Dense-fish model evaluation

Script:

```text
R:28_multi_fish_ets_backtest.R
```

Purpose:

Compare:

```text
ETS(A,N,N)
```

against:

```text
NAIVE
```

using walk-forward out-of-sample testing.

Evaluation metrics include:

```text
MAE
RMSE
MAPE
80% interval coverage
interval width
```

The model is selected per fish.

There is no assumption that ETS is best for every fish.

---

## Stage 28A — Recent-week coverage

Script:

```text
R:28A_recent_week_coverage.R
```

Purpose:

Inspect the most recent data coverage.

This is especially important because PriceCatcher is continuously updated and not all fish have the same observation frequency.

A dense fish may have 7 active days in a week, while sparse fish may only have one.

The latest raw source week is also treated carefully so that incomplete weeks are not accidentally used as completed modelling weeks.

---

## Stage 28B — Sparse-fish model evaluation

Script:

```text
R:28B_sparse_fish_backtest.R
```

Purpose:

Evaluate sparse fish separately instead of pretending all fish have dense weekly coverage.

The current sparse set includes:

```text

Ikan Merah
Jenahak
Siakap Putih
Tenggiri
```

The sparse backtest currently uses 79 completed weekly observations across the longer sparse series and produces 67 walk-forward test predictions.

Current sparse backtest result:

```text
Ikan Merah     ETS_BETTER
Jenahak        NAIVE_BETTER
Siakap Putih   NAIVE_BETTER
```

# 8. Forecast eligibility rules

Script:

```text
R:29.1_final_forecast_eligibility.R
```

This is the main decision layer.

It decides:

- whether a fish has enough history,
- whether its data is dense or sparse,
- whether the data is fresh enough,
- which backtest results apply,
- which model should be used,
- whether forecast intervals are acceptable,
- whether the fish is production-ready.

## Data density categories

Current logic includes:

### DENSE

A fish is dense when:

```text
>= 40 usable dense weeks
AND
>= 70% of dense weeks have >= 5 active days
```

### SPARSE

A fish is sparse when:

```text
>= 20 usable sparse weeks
```

### VERY_LIMITED

Used when a fish has historical observations but does not meet the dense/sparse support criteria.

### NO_DATA

No usable PriceCatcher observations.

---

# 9. Freshness rules

Freshness is calculated from the latest actual PriceCatcher observation.

Current thresholds:

```text
<= 7 days   -> CURRENT
<= 28 days  -> RECENT
> 28 days   -> STALE
no data     -> NO_DATA
```

A stale fish is not forecast in production.

This is particularly important for fish where PriceCatcher coverage has stopped.

# 13. Reference week policy

The model deliberately distinguishes between:

```text
latest actual PriceCatcher observation
```

and:

```text
latest completed modelling week
```

Example:

```text
Latest raw observation:       2026-08-27
Current week start:           2026-08-24
Latest completed week:        2026-08-17
```

The incomplete current week is not treated as a completed modelling week.

This prevents a partially observed week from becoming the model's reference point.

# 15. Forecast range interpretation

`expected_price` is the point estimate.

`lower_bound` and `upper_bound` form the forecast range.

The range is model-derived rather than an arbitrary business rule.

For ETS forecasts, it comes from the model prediction interval.

For Naive forecasts, the empirical historical naive absolute-error distribution is used to construct the interval.

The backend should store all three values:

```text
expected_price
lower_bound
upper_bound
```

The frontend can then show:

```text
Expected: RM X
Likely range: RM Y – RM Z
```

Do not recompute the interval on the frontend.

---

# 16. Directional outlook

Script:

```text
R:31_direction_outlook_validation.R
```

Directional movement is treated separately from the price forecast itself.

The current meaningful movement threshold is:

```text
RM 0.25
```

Signals are only emitted when validated evidence meets the minimum evidence rules.

Valid production directional values are:

```text
LIKELY_INCREASE
LIKELY_DECREASE
NO_STRONG_SIGNAL
```

A `NAIVE` price forecast has no model-based directional information because the Naive point forecast is the current/reference price.

The direction subsystem can therefore use a validated historical strategy instead.

Current direction strategies considered include:

```text
model_signal
last_week_signal
four_week_signal
four_week_median_signal
```

Only strategies meeting the configured evidence requirements are selected.

# 24. Daily refresh behaviour

Because PriceCatcher updates daily, the production process should be designed to run repeatedly.

A daily refresh should:

1. Obtain the latest official PriceCatcher CSV manually.
2. Place it in the expected raw-data location.
3. Run the R production refresh.
4. Recalculate the cleaned series.
5. Recalculate model eligibility and model selection.
6. Recalculate the four-week forecast.
7. Recalculate directional evidence.
8. Rebuild database staging.
9. Load/update the database.
10. Expose the current forecast through the API.

The forecast itself is not expected to change every day simply because a new CSV exists. The model deliberately uses completed weeks as its production reference.

---

# 25. Incremental vs full refresh

The safest implementation for the current project is a **repeatable full rebuild of the forecasting outputs from the accumulated official raw data**.

Why:

- the dataset is manageable for the current project scope,
- model selection is recomputed consistently,
- cleaning rules are applied consistently,
- sparse/dense classification can change over time,
- stale/current status can change,
- historical corrections can be reflected.

The backend/database can then use an upsert/versioning strategy rather than blindly inserting duplicate forecast rows.

The R pipeline should remain reproducible from source files.

---

# 26. Database upsert principle

Recommended natural uniqueness for a forecast row:

```text
seafood_item_id
+
location_id
+
forecast_model_version_id
+
forecast_week_start
```

The R staging output also validates a corresponding natural key:

```text
canonical_name
+
location_name
+
model_version_name
+
forecast_week_start
```

There must not be duplicate forecast rows for the same natural key.

The database implementation may use a UUID primary key for `price_forecast_id`, but should enforce a suitable unique constraint/index on the natural key.

---

# 27. Do not use fish names as database foreign keys

Bad:

```text
price_forecast.seafood_item_id = "Kembung / Pelaling"
```

Correct:

```text
price_forecast.seafood_item_id = <seafood_item UUID>
```

The string name is only a lookup/display key.

This matters because:

- names can change,
- aliases exist,
- multilingual names exist,
- WWF and PriceCatcher names need mapping,
- database integrity requires real foreign keys.

# 29. Frontend responsibilities

The frontend should:

- request forecast data from the backend,
- display the reference price,
- display the expected price/range,
- display model/data-quality messaging when appropriate,
- display the directional outlook when present,
- handle `NO_STRONG_SIGNAL` gracefully,
- handle unavailable fish gracefully.

The frontend should **not**:

- run R,
- calculate ETS,
- calculate forecast intervals,
- choose the forecasting model,
- recalculate data quality,
- invent directional signals,
- query PriceCatcher directly.

---

# 30. Suggested user-facing semantics

Recommended interpretation:

### VALID

Strong production support based on the current rules.

### SPARSE_DATA

Current forecast is available, but historical observation density is lower than dense fish.

This does **not** mean the forecast is unusable. It means the user-facing system should be more conservative.

### UNAVAILABLE

Do not show a fabricated forecast.

Explain that a forecast is currently unavailable because the underlying PriceCatcher coverage is stale or absent.

# 36. Common errors and fixes

## Error: PriceCatcher CSV not found

Example:

```text

```

Fix:

Place the official CSV in the expected raw-data directory.

Then rerun the refresh.

## Error: Mapping file not found

Example:

```text
lookup/price_forecast_fish_mapping.csv
```

But the actual file is:

```text
data/lookup/price_forecast_fish_mapping.csv
```

Fix:

Use:

```r
lookup_dir <- "data/lookup"
```

---

## Error: pipeline script not found

Example:

```text
01_prepare_pricecatcher_data.R
27_clean_multi_fish.R
```

when the actual R folder contains:

```text
R:23 multi_fish_price_series.R
R:27_multi_fish_cleaning.R
...
```

Fix:

Check exact filenames:

```r
list.files("R", full.names = TRUE)
```

Then make `R:34_daily_forecast_refresh.R` reference the actual filenames.

Do not guess names.

---

## Error: latest_week does not exist

This happened earlier because `latest_week` was effectively represented by other fields after the joins.

The corrected production eligibility printouts use:

```text
completed_week
```

for the actual production reference week.

Do not reintroduce `latest_week` into print/select statements unless that column is explicitly created.

---

## Error: forecast horizon validation

When comparing R Date vectors, avoid fragile `identical()` checks if one side may have different attributes/classes.

A safer membership/set comparison is:

```r
all(expected_forecast_weeks %in% actual_forecast_weeks) &&
all(actual_forecast_weeks %in% expected_forecast_weeks)
```

The current production validation uses the safer approach.

---

## Error: outlook column missing

Be careful not to validate:

```r
api_forecast$outlook
```

if the API export intentionally contains only an `outlook_label`.

Validation must match the actual production API schema.

The integrated forecast retains:

```text
outlook
outlook_label
directional_outlook
directional_outlook_label
```

but downstream exports may intentionally select a subset.

# 52. Current modelling interpretation

The model is **not** claiming:

> "This fish will definitely cost RM X."

It is producing:

- a point estimate,
- an uncertainty range,
- a model/quality status,
- optionally a validated directional outlook.

The system should use language such as:

```text
Expected price
Likely range
Likely to increase
Likely to decrease
No strong directional signal
```

rather than deterministic guarantees.

---

# 53. Why Naive can be the selected model

This is intentional.

For several fish, the benchmark that simply carries the latest price forward performed better than ETS in walk-forward testing.

That means the system is allowed to choose:

```text
NAIVE
```

rather than forcing a more complex model.

This is a feature, not a failure.

---

# 54. Why some forecasts show "No strong directional signal"

A price forecast and a directional signal answer different questions.

Example:

```text
Expected price: RM15.90
Forecast range: RM14.90–RM16.90
Direction: No strong directional signal
```

This means the model supports a forecast around the current level but the validated direction rules do not have enough evidence to confidently call an increase/decrease.

That is intentionally conservative.

---

# 55. Why the forecast does not use the latest partial week

PriceCatcher data is daily.

A week that has only been partially observed should not be treated as complete.

Example:

```text
2026-08-24 week
```

had only partial data at the time of the August 27 source snapshot.

The pipeline therefore used:

```text
2026-08-17
```

as the completed reference week.

This prevents an artificial shift caused simply by the calendar being mid-week.

---

# 56. When a stale fish becomes forecastable again

No code change should be required.

Suppose:

```text
Ikan Gelama
```

is currently stale.

When new official PriceCatcher records appear for that fish:

1. the latest observation date updates,
2. freshness status is recalculated,
3. recent weekly coverage is rebuilt,
4. eligibility is reevaluated,
5. model selection is reconsidered,
6. a forecast may become available again.

The data, not a manual override, should drive this transition.

---

# 57. When to create a new model version

Create a new model version when there is a material methodology change, such as:

- changing the model family,
- changing eligibility rules,
- changing forecast interval methodology,
- changing the directional strategy,
- changing the production horizon,
- changing how the reference series is built.

A normal daily refresh with the same methodology does not necessarily require a new version.

The current version:

```text
2026-08-v1
```

should therefore be treated as the current methodology version unless the team deliberately changes the method.

# 66. Final note for the SukaSeafood team

The current August 2026 build is a **production-ready forecasting pipeline for the current project scope**, with conservative eligibility rules and explicit handling of sparse/stale data.

It should not be described as a universal forecasting model for every seafood item.

Instead, the correct description is:

> **SukaSeafood uses validated per-fish model selection for supported Selangor seafood price forecasting. Depending on the amount and freshness of PriceCatcher data available for each fish, the system selects ETS or a Naive benchmark, produces a four-week price outlook, estimates an uncertainty range, and provides a directional signal only when historical evidence is strong enough.**

The system is designed to improve automatically as more official PriceCatcher data becomes available and can be extended later to additional fish or new forecasting methods, provided the same validation and versioning discipline is maintained.
